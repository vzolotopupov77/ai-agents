## Итеративный план

### Итерация 1 — Telegram и первый сквозной диалог через LLM

**Цель итерации:** бот в личном чате через long polling получает текст пользователя и возвращает ответ, собранный моделью с учётом системной роли из конфигурации.

- [x] Репозиторий и запуск приложения локально из документации проекта.
- [x] Настройки из окружения (токены, endpoint и параметры модели — по vision).
- [x] Long polling к Telegram и обработка входящего текста.
- [x] Вызов LLM по конфигурации; запрос: системная роль + текущая реплика пользователя.
- [x] Ручная проверка: вопрос в чат → осмысленный ответ.

**Готово, если (DoD)**

**Самопроверка**

- [x] Процесс стартует без падений при валидном `.env`.
- [x] В stderr — ожидаемые записи журнала, без секретов.
- [x] На тестовый вопрос приходит финальный ответ ассистента; нет необработанного исключения в цепочке.

**Пользователь**

- [x] На произвольный текст в личке приходит ответ от бота (ответ строится моделью, не заглушка приложения).
- [x] Ответ по смыслу согласован с заданной ролью и формулировкой вопроса.

### Итерация 2 — Память диалога и лимит истории

**Цель итерации:** бот помнит недавнюю переписку и «забывает» начало после превышения лимита.

- [x] Хранение истории беседы в памяти процесса на чат.
- [x] Несколько репли подряд с опорой на предыдущий контекст.
- [x] Обрезка истории по настраиваемому максимуму сообщений.

**Готово, если (DoD)**

**Самопроверка**

- [x] Две связанные реплики дают второй ответ с учётом содержания первой.
- [x] При искусственно малом лимите истории ранние факты перестают учитываться в ответах.

**Пользователь**

- [x] Выполнен мини-сценарий «вопрос → уточнение с отсылкой к прошлому».
- [x] После серии сообщений содержание «старых» реплик не воспроизводится в ответах.

### Итерация 3 — /start и сбои API

**Цель итерации:** понятное приветствие; при недоступности модели пользователь видит короткий нейтральный текст без технических подробностей.

- [x] Обработка команды старта с приветствием без лишнего вызова модели (если так решено для MVP).
- [x] При ошибке сети/API — одно понятное сообщение; детали только в журнале.
- [x] Единое правило: не дописывать в историю «ломкий» или пустой ответ ассистента.

**Готово, если (DoD)**

**Самопроверка**

- [x] `/start` ведёт себя как зафиксировано для MVP (без лишних вызовов LLM).
- [x] При ошибке API в чат уходит сообщение; в логе есть детали без секретов (проверено: неверный `OPENROUTER_API_KEY`).

**Пользователь**

- [x] Видно приветствие на команду старта.
- [x] При неверном ключе API — короткий нейтральный текст в чате, без стектрейсов и ключей. Обрыв сети вручную не проверялся (код обрабатывает сетевые/API-сбои тем же путём).

### Итерация 6 — Финансовый советник: модель учёта и `/report`

**Цель итерации:** перейти на роль финансового советника по [idea.md](./idea.md); в памяти процесса — хранилище транзакций по §5 [vision.md](./vision.md); команда **`/report`** отдаёт текстовый отчёт (баланс, агрегации по категориям) **без** вызова LLM. Извлечение операций из текста **ещё не** делается.

- [ ] Модель `Transaction` и хранилище в памяти на `chat_id` (как в vision §5).

- [ ] Команда `/report`: корректно работает на пустом списке и после появления записей (для проверки итерации 6 допустимо временно добавить тестовую запись из кода или минимальную отладочную команду — по согласованию в PR, без усложнения продукта).

### Итерация 7 — Structured output из текста

**Цель итерации:** сообщения пользователя о тратах и доходах разбираются LLM с **structured output**; при **`found=True`** создаётся `Transaction` и отправляется подтверждение; при **`found=False`** — ответ советника без записи (см. vision §6, §7).

- [ ] Pydantic-схема извлечения (например `TransactionExtract`) и вызов API с `response_format` / совместимым режимом.
- [ ] Интеграция в обработчик текста: запись в хранилище, обновление истории диалога по согласованному правилу.
- [ ] Ручная проверка: фразы с суммой и без — ожидаемое поведение и отсутствие дубликатов при unclear edge cases (по возможности).

**Готово, если (DoD)**

**Самопроверка**

- [ ] Ошибка API обрабатывается как в итерации 3; история не засоряется.

**Пользователь**

- [ ] Типичная трата/доход в одном сообщении попадает в `/report`.
